# 2026.327.1351 — feat(generator): never resolve a retired repo into the corpus

## Summary

The corpus generator now has an explicit, data-driven **retirement** exclusion, and the remote walk honours it through the SDK seam landed in opencharly/sdk#626 (`candywalk.CollectEntitiesRemoteScoped` + `RefScope`, released as `v0.2026327.1226`).

**The file.** `retired.cue` at the corpus root (the generator's `--root`) lists repos the corpus has retired:

```cue
retired: [
	"github.com/opencharly/pod-immich-ml",
]
```

It is authored data, so it is CUE, and its shape is `#Retired` in this plugin's served schema (`schema/marketplace.cue`) — the same schema published over Describe. `retire.go` validates the file against that definition at read time: because `#Retired` is a CLOSED definition, a typo'd field, a malformed list or an unqualified repo path fails the generation instead of silently retiring nothing. A missing file means "nothing retired" (the shape every corpus had before this change). A retired repo pinned by the refs list is an authoring contradiction: the ref is dropped and `readKinds` fails the run, naming it.

**Why a list and not a structural rule — measured, twice.**

opencharly/plugin-marketplace#63: after the refs list dropped every `pod-immich-ml` pin, `charly marketplace generate` still published `immich/skills/immich-ml`. An instrumented walk recorded the chain: `pod-immich-ml:v2026.239.1604` is declared by `distro-fedora@v2026.256.1134/{box/immich-ml,candy/charly-marketplace}/charly.yml` and `:v2026.274.0811` by `distro-cachyos@v2026.319.0820` and `@v2026.319.1138`, both files each — old trees reached through stale subpath pins in `pod-dsh@v2026.292.2042/charly.yml:18-20` and `layer-agentteams@v2026.319.1239/box/cachyos-base/charly.yml:39`, while the refs list pins those two repos at `v2026.325.1900` / `v2026.327.0930`.

Two structural closure rules were implemented and measured against the full 362-skill corpus. Both were rejected because they cut PUBLISHED content alongside the retired one:

- "only corpus-owning files contribute refs" → removed `immich-ml` **+ 11 live skills** (`ai-toolkit`, `ai-toolkit-layer`, `qwen3-tts`, `openclaw-desktop`, `openclaw-full`, `openclaw-full-layer`, `openclaw-full-ml-layer`, `fedora-coder`, `fedora-test`, `clawsweeper-review`); the newest distro boxes are the legitimate carriers of pod repos' skills.
- "an older tree stops extending the closure" → removed `immich-ml` **+ 6 live skills** (`openclaw-desktop/full/full-layer/full-ml-layer`, `fedora-coder`, `fedora-test`), whose only remaining carrier chains are stale trees.

A retired repo and a live repo reachable only through an old tree have the same shape, so no rule that walks the graph can separate them. Retirement is data.

**Also in this change**

- `readKinds` walks via `CollectEntitiesRemoteScoped`; the walker's full-closure contract is untouched for every other caller.
- `go.mod`: `github.com/opencharly/sdk v0.2026327.1226` (+ the `spec` version that requirement forces).
- The `marketplace` skill documents `retired.cue`; `README.md` names it in the `--root` contract.
- Honouring a ref's SUBPATH (so a file import stops dragging a whole old tree in) is filed as opencharly/plugin-marketplace#64, not silently folded in here.

**Scope: mechanism, not symptom-completion.** This PR alone does not remove `immich/skills/immich-ml` from the published corpus — the retirement list that does is data, and it lands in the opencharly/marketplace PR (with the pin bump and the regeneration), which is the PR that closes opencharly/plugin-marketplace#63. Merging this one first is what makes that PR possible, and it is a no-op on every corpus without a list.

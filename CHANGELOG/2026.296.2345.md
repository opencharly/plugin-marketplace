# 2026.296.2345 — fix(corpus): fetch corpus sources files-only — the walk reads no submodule

Agent: charly-spec279

## Summary

The corpus walk now fetches its sources **files-only**: `readKinds`' remote resolver
becomes `refs.DownloadRepoFiles` (from the `github.com/opencharly/spec` release that
introduces it) instead of `refs.DownloadRepo`.

A corpus source is read for its OWN TREE — `charly.yml` and the `.agents/` trees — so the
fetch should certify exactly that. `refs.DownloadRepo` populates **every** submodule the
fetched repo declares and fails the whole fetch when one cannot be fetched: right for a
`--repo` cache, and fatal here. Measured cold, on the repo that forced the producer fix
(`opencharly/opencharly:v2026.296.2037`, 412 declared gitlinks):

That is `opencharly/spec#279`, and it is why the umbrella pin was withdrawn from

corpus could not reach them. The same population had already been measured as a pure
cost on this very walk in `opencharly/spec#267` (431 gitlinks, ~3 min cold, 272 MB
transient, none of it read).

## The change

```go
- ents, err := candywalk.CollectEntitiesRemote(roots, refs.DownloadRepo)
+ ents, err := candywalk.CollectEntitiesRemote(roots, refs.DownloadRepoFiles)
```

One line, no seam change: `candywalk.RemoteResolver` is
`func(repoPath, version string) (string, error)` and the files-only fetch has exactly
that signature, so the SDK is untouched and the `--repo` cache keeps the whole-project
fetch it needs. The two fetches also have separate cache entries
(`<cache>/.files/<repo>@<version>` vs `<cache>/<repo>@<version>`), so a corpus run and a
`--repo` run never re-download each other's work.

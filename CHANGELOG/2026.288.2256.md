# 2026.288.2256 — fix(extract): write the separator once, so the file reads back byte-for-byte

## Summary

`charly marketplace extract` wrote each extracted `SKILL.md` as `skillFrontmatter(name, s.Description) + "\n" + s.Content`, but `skillFrontmatter` **already** ends with the `---\n\n` separator that the frontmatter splitter strips exactly once. Every extracted file therefore read back with one leading newline the entity did not have.

Two consequences, and the second is the dangerous one:

- **Loud, in the mixed state** (the wave has written the files but not yet deleted the inline body): the generator's own agreement guard rejects the repo — `skill "agents": the node's inline `content:` and its file disagree — delete the inline body and keep the file` — so a wave repo cannot be gated at all.
- **Silent, once that body is deleted** (the wave's actual end state): the file wins, nothing errors, and the corpus gains a leading blank line in every moved skill body. `drift` cannot see it, because both sides regenerate from the same file.

The fix writes the separator once. The new test reads the written file back **through the reader** and compares it with the entity byte for byte — content, description and every reference — and carries a second case whose body's first lines are blank, so a "trim leading newlines" fix fails it too.

Measured on the pilot repo `layer-charly-internals` (20 skills, 25 references): the pre-fix writer mismatched **20 of 20 bodies**; descriptions and all 25 references were clean. Post-fix: 0 of each.

**Disclosed, not hidden.** The same round trip shows ONE further corpus artifact differing between the inline and the file source: `.well-known/skills/index.json`, whose per-skill `files` array follows the manifest's document order on one path and the reader's stem sort on the other. That is a different mechanism (order canonicalization, not the bytes this writer writes); the fix belongs on the emitter side, and it is filed as `#28` and **not** changed here.

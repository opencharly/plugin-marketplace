# 2026.288.2313 — fix(generator): canonicalize a skill's reference order, so the corpus is byte-identical across a move

## Summary

`.well-known/skills/index.json` lists each skill's `files` in `s.References` order, and that order depended on **where the prose came from**:

```console
$ sed -n '107,110p' candy/plugin-marketplace/emit_dispatcher.go
			for _, r := range s.References {
				files = append(files, "references/"+r.Name+".md")
			}
$ grep -n 'sort.Slice' candy/plugin-marketplace/emit_dispatcher.go
115:	sort.Slice(idx.Skills, func(i, j int) bool { return idx.Skills[i].Name < idx.Skills[j].Name })
$ sed -n '174,175p' <sdk>/candywalk/skillfile.go
	sort.Slice(out, func(i, j int) bool { return out[i].Stem < out[j].Stem })
	return out, nil
```

The SKILLS array is sorted; each skill's own `files` array is not — and the entity form arrives in the manifest's **document order** while the file form is **stem-sorted** by the reader, because a directory listing has no document order to reproduce. So a skill reordered its own entry in the index simply by moving house: the corpus could not be byte-identical across a move, which is the invariant this whole relocation is proven by (`plugin-marketplace#28`).

The fix canonicalizes the order at the ONE funnel every skill enters the model through — `readkinds.go`, immediately after the file-vs-entity reconciliation — so no source form can escape it. The file form's sort cannot be the fix: document order is not recoverable from a directory listing, so the entity form has to agree with the file form instead of the other way round. Nothing depends on the other order: each reference is emitted as its own `references/<name>.md`, and the `files` array is a manifest of those files, fetched one by one by the consumer.

**Measured consequence, disclosed rather than hidden.** The committed corpus carries 353 skills; 7 of them have more than one reference, and exactly ONE — `git-workflow` — has a `files` order that is not already canonical. So one array inside one generated artifact reorders, and the marketplace repo's own deploy gate reports exactly that one stale artifact until its regeneration lands. That is the normal producer-first order, and it is **filed and announced, not parked**: `opencharly/marketplace#483` tracks the owed regeneration, with `BLOCKS` posted on both threads.

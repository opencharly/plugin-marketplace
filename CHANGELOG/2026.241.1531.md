# 2026.241.1531 — fix: resolve duplicate entity names deterministically instead of last-write-wins

## Summary of changes

`readKinds` did this over a collection with no defined order:

```go
ks.Skills[e.Name] = s      // last write wins, silently
```

So when one entity **name** arrived from more than one source, the winner was whichever happened to
arrive last — no warning, no gate, no determinism.

### It is not hypothetical — measured on the live closure

A probe calling the same `candywalk.CollectEntitiesRemote(roots, refs.DownloadRepo)` the generator
calls:

```
total skill entities collected: 696
distinct skill names:           310
names arriving MORE THAN ONCE:  82
```

Almost all of that is harmless, and it is worth saying so rather than overstating: for **79** of
those names the two bodies are byte-identical, so the choice never mattered. For **three** the
bodies **differ**, which means the published content of those skills depended on iteration order:

```
hermes-skill           3a633d591126@v2026.237.936   35ac48ccc696@v2026.239.1605
selkies-core-skill     99b28d1c8ca1@v2026.237.808   d5780354c4fc@v2026.240.2344
xfce4-terminal-skill   a089ad841c7e@v2026.237.1057  b0529bdfbe7b@v2026.239.1558
```

(bodies hashed after `yaml.Marshal` of the entity value)

**Cause:** the same repo resolved at two tags in one closure. The refs list pins
`pod-hermes:v2026.239.1605` directly, while something in the transitive closure still pins
`pod-hermes:v2026.237.936`. Both are fetched; both yield a `hermes-skill`.

### The rule

**Highest source tag wins** — and that is not an arbitrary tiebreak. In every one of the three
observed conflicts the refs list pins the **newer** tag directly and the older arrives
transitively, so *"highest tag"* is the same thing as *"the refs list's explicit pin"*. It is also
how Go's MVS resolves a module required at two versions.

| Case | Resolution |
|---|---|
| local vs fetched | **local wins** — the tree being generated from is the authority |
| two pinned tags | **higher CalVer wins**, compared **numerically** |
| pinned vs unparseable (a branch ref) | **pinned wins** |
| genuine tie | stable comparison on `SourceRoot`, never order-dependent |

The numeric comparison has its own test, because the text trap is live: **`"v2026.239.1605"` sorts
BELOW `"v2026.239.936"`** lexicographically (`'1' < '9'`), so a string comparison would pick the
*older* tag on exactly the pair this fix exists to resolve.

### This changes nothing about today's corpus — deliberately

Regenerating with the deterministic resolver produces a **byte-identical 303-file corpus**:
last-write-wins happened to land on the same winners. That is the point. The corpus was correct
**by luck**; now it is correct **by construction**.

## Summary

`charly marketplace generate` exited **0** and emitted an `openclaw-layer` body matching neither
the branch file nor the newest tag. The issue left one question open — *which code path produces
a body from a node with no `content:` and no matching file?* — and this is the answer, with the
fix that makes the emitted body the pinned tree's body.

### Where the body came from

**Not from the pinned tree at all.** `readkinds.go` unions every repo in the transitive closure
(`CollectEntitiesRemote`), then resolves each `(kind, family, name)` identity to ONE winner
(`dedupeEntities` -> `preferEntity`, `resolve.go`). `preferEntity` ranked the candidates by the
CalVer tag it could parse out of the fetched cache dir — `if iOK != cOK { return cOK }`.

The project pins `layer-openclaw` at a **branch** (`feat/skill-bodies-to-repo-root`), and a
branch ref carries no CalVer: `tagRank` returned `ok=false` for it, so **any** transitive tag
outranked it. The closure also reaches the pre-rename `layer-charly-openclaw@v2026.271.2234`,
whose `openclaw-layer-skill` node still carries the body **INLINE** — the pre-relocation shape.
That node won. `fillSkillFromFile` found no `SKILL.md` in that tree at all — it holds none, at
any path — so it took the transitional inline branch and the generator published it, rc=0. The
pinned tree was never read, because the winner was a DIFFERENT ENTITY of the same identity,
chosen by tag rank.

The emitted document is byte-identical to that node's inline `content:` (`e1b94367…`, 1778B /
1772 characters), and the issue's own whole-file hashes reproduce exactly on this run
(`35a2e3a6…` = the branch file, `82e7f941…` = the file the pre-fix arm emitted).

### The fix

The refs list is the ONE generation input, so **the ref the project names DIRECTLY is the
authority** — which is the law the CalVer comparison was only a proxy for, as `resolve.go`'s own
comment already claimed ("'highest tag' is the same thing as 'the refs list's explicit pin'").
It is now carried explicitly instead of inferred from a ref's shape:

- `pinAuthority` (`resolve.go`) holds the generator's OWN roots and the `candy:`/`require:` refs
  those roots declare, keyed exactly as candywalk keys a fetched root's `Entity.Namespace`
  (`<repo>:<version>`) — so the test is a map lookup on the entity, not a re-parse of a path;
- `preferEntity` checks it **before** the CalVer rank: local-over-fetched, then
  directly-pinned-over-transitive, then highest tag;
- the local/fetched distinction is decided by **root membership**. `candywalk` sets an entity's
  `SourceRoot` to the local root's directory, never to `""`, so the old empty-string sentinel
  identified nothing and a local entity could not win at all — that dead arm is deleted.

Transitive refs are not disqualified: a repo reached through the closure still publishes its own
skills. Only a COLLISION on one identity is decided by the project's own pin — which is the case
this file exists for.

**Two `openclaw` bodies had moved, not one.** The second (`openclaw`) was shadowed by the same
mechanism, from the monorepo-era inline copy of the `openclaw` candy still carried by old
snapshots: `layer-supervisord@v2026.239.1300`, `layer-sway-desktop@v2026.238.2103`,
`layer-openclaw-full@v2026.238.2103`, `layer-agent-forwarding@v2026.238.1851`,
`layer-hermes-playwright@v2026.238.2102`. Both are
corrected by this one change, and the whole emitted corpus moves by exactly those two files.

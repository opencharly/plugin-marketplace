# 2026.288.1355 — feat(generator): read a skill's prose from the file its repo owns, and add `marketplace extract`

## Summary

The marketplace generator now reads a skill's prose from the **file the repository owns**, instead of only from the in-line `content:` of its `skill:` node — and it can move a body there.

Three pieces:

- **`skillfile.go`** — `skillTrees` and `fillSkillFromFile`. The read happens **inside `readkinds.go`'s decode loop, after `dedupeEntities`**, so the tree that is read is the winner's own `SourceRoot`. That placement is the whole point (F13): 293 of the 355 published identities arrive from more than one repo, and reading anywhere else — or from the generator's own root — publishes a body `preferEntity` did not choose. Three rules are loud on purpose: the file wins when it exists; an in-line body that **differs** from it is an error naming both; **neither** body anywhere is an error, because silence there drops a published skill from the corpus.
- **`command.go` + `extract.go`** — `charly marketplace extract`, the third mode beside `generate` and `drift`. It reads a repo's own manifests at the file level (`candywalk.ReadEntityFile` over the root `charly.yml` and `candy/*/charly.yml`) and writes `<root>/<tree>/<name>/SKILL.md` plus `references/<stem>.md` in the authored, marker-less shape the reader parses back. It never writes the corpus, and it never reaches the network.
- **Two pins**, and there are two for a reason: `sdk v0.2026288.1246` carries the reader, and `spec v0.2026288.1242` carries `#Candy.skills`. The sdk tag's own `go.mod` still requires the pre-`spec#247` spec, so MVS leaves `spec.Candy.Skills` undefined until spec is moved as well — found by running it, not by reading it.

## How tested

```

$ go test ./...         rc=0   (all 8 new tests pass)
```

The eight tests fail without the change — `fillSkillFromFile` and `extract` did not exist, so the test files do not even compile against the pre-change tree. They pin: the moved shape (routing-only node + its file, id defaulting to the node name, no generator marker), the in-line form still passing through untouched, **no body anywhere** as an error, a node/file **disagreement** as an error, a declared tree being honoured, and `extract`'s round trip **plus its no-op** once the wave deletes the in-line body (asserted by deleting the written file and re-running: a verb that still saw a body would recreate it).

The declared-tree case is exercised through `extract`, not only through the reader, and its before/after was run rather than asserted — with the owning-candy lookup in place it passes; with the skill's-own-node lookup it fails:

```
$ go test ./ -run TestExtract_Honours -count=1      → ok
$ sed -i 's/trees\[s.Owner\]/trees[e.Name]/' extract.go && go test ./ -run TestExtract_Honours -count=1
FAIL
$ sed -i 's/trees\[e.Name\]/trees[s.Owner]/' extract.go && go test ./... → ok   (lint 0 issues, gofmt clean)
```

The corpus arm, `drift`, was **attempted and is blocked by `#250`** — not passed, not skipped: it dies in `collect entities` on an unsubstituted `<kind>-<name>:<tag>` template scraped from a CHANGELOG's prose, before any skill is read, and it does so identically with the shipped generator. Its expected result — a byte-identical corpus — is an expectation here, not a claim: this diff changes how a body is **read**, never what is **written**.

# 2026.289.0132 — fix(resolve): the dedupe key carries the FAMILY, so two families may publish one skill name

## Summary

**The emitter's dedupe key now carries the FAMILY, so two families may publish a skill with the same name.** `dedupeEntities` collapsed entities that share a `(Kind, Name)` and `preferEntity` let tag order pick the survivor — so when two families declared one name, the higher CalVer won, and the loser's file *and the dispatcher row its `triggers:` fed* were pruned from the corpus.

**The family is identity, not metadata.** The corpus is per-family (`<family>/skills/<name>/SKILL.md`) and a skill is addressed `/charly-<family>:<skill>`, so `layer-crabbox` (family `tools`) and `plugin-crabbox` (family `check`) both declaring `crabbox` are **two different skills**, and every consumer can already tell them apart. Keying on `(Kind, Name)` alone made them fight, and made *which one you get* a function of tag order — no source repo controls it.

**The measured instance, from tonight.** `opencharly/marketplace#490` (the daily refresh, merged as `8cca9140`) advanced both of those pins, and the winner **inverted**:

```console
$ git diff --name-status <base>...<head> | grep crabbox
D	check/skills/crabbox/SKILL.md
A	tools/skills/crabbox/SKILL.md
```

A routine pin refresh silently **swapped a published, trigger-bearing skill for a different one** and took the `/charly-check:crabbox` dispatcher row with the loser. The repo's own drift gate cannot see it: regeneration reproduces exactly that output, because it *is* the output. That is this programme's own clause about the multi-source identities, with a mechanism and a measurement — the objective's *"or the corpus silently reverts for the 293 multi-source identities"*.

**Where the family comes from, and why not from the walker.** `candywalk.Entity` carries `Name`, `Namespace`, `Dir`, `Kind`, `Value`, `SourceRoot` — **no `Family`**, and it must not gain one: the walker is a shared generic kit, and the family is a `skill:` body attribute (`spec.Skill.Family`). So the key is computed in the emitter (`entityFamily`), which already owns the skill shape — the same boundary this repo's `AGENTS.md` draws.

**And the same collapse existed one step later.** `kindSet.Skills` was a map keyed by **node name**, so two same-named skills in different families would have been dropped *there* instead — the fix would have been invisible. It is a slice now; the model sorts each family's skills by name, so no key is needed downstream.

**Producer → consumer, stated as the next step rather than implied.** Fixing the key does not by itself republish the pruned skill: the emitter must land, tag, and then `marketplace`'s generator pin (`tools/marketplace-cli/go.mod`) must be advanced with a regeneration, exactly as `#487`/`#490` did for the relocation. I will file that row on `marketplace` once this has a tag, so it names a real version.

Closes #20

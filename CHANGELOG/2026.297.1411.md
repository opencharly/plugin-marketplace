# 2026.297.1411 — fix(drift): a runnable, CI-owned drift gate — and the corpus commit it reproduces (#42)

## Summary

`charly task skills:drift` was red in four different ways at once, and no CI job ran
it, so nothing could see it. This change makes the gate runnable, gives CI a job that
owns the GENERATOR side of the corpus contract, and re-points the corpus pin at the
commit this generator actually reproduces.

**Four defects, one root: the recipe was written against an interface that does not
exist.**

1. **The parameter was `out` — lower case.** The task runner's expansion grammar
   matches UPPER-CASE names only (`sdk/kit/checkvars_expand.go:16-17`), so the value
   never reached the command and the shell dropped the empty word: "--out: expected
   string value but got EOL". It is `CORPUS` now.
2. **`--root` named the wrong tree.** The generator's ONE generation input — the refs
   list, `candy/charly-marketplace/charly.yml` — lives INSIDE the corpus checkout, so
   `--root` must name it. Both flags now name the corpus checkout.
3. **The "the tree is committed" step ran `git status` in THIS repo**, so it checked
   the plugin's tree, not the corpus's. It names the corpus now.
4. **The drift step carried no `timeout:`.** The per-step never-hang bound is 1m30s, and
   the drift resolves EVERY corpus source (the refs list names ~1200 repos at pinned
   versions) before it compares a single byte — measured 11m48s in the marketplace
   repo's own deploy workflow — so the step was killed at the ceiling and the gate
   reported a TIMEOUT where the truth was "slow, and green". The bound is a hang guard,
   not a budget.

**The SDK pin** (`candy/plugin-marketplace/go.mod`, v0.2026296.2152 → v0.2026297.129).
The old version's `acceptedRef` refuses EVERY `github.com/opencharly/charly` ref, and
the corpus's refs list relies on the bare repo-root form
(`@github.com/opencharly/charly:v2026.297.0032`) being a corpus source. A standalone
build of the generator therefore dropped the charly corpus source, the closure twin
`layer-charly-internals` won, and a rule-renumbering difference (R2/R3 → R3/R4) left 9
stale artifacts. The new version admits the bare repo-root form and refuses only the
SUBPATH form (`opencharly/sdk#468` → `opencharly/sdk#470`). The declared-refs fix that
PR #47 adopted (`opencharly/sdk#467`) is present in both versions, so the bump is a
strict superset, not a revert.

**The corpus pin** (`var: MARKETPLACE_REF` and the literal that duplicates it by
design, e802da68 → cc10955e). The current generator no longer reproduces the Oct-15
corpus commit; cc10955e is the corpus's current `main` head, which is the invariant this
repository declares.

**A CI job** (`.github/workflows/drift-gate.yml`). The marketplace repo's deploy
workflow owns the CORPUS side of the contract; nothing owned the GENERATOR side. The
job runs the recipe on every merge to `main`, against the corpus commit this repo
DECLARES, read out of `candy/plugin-marketplace/charly.yml` rather than repeated as a
second literal — one pin, not two that can drift.

It runs on `main` and not on `pull_request`, and that is a design constraint, not an
omission. A generator change that alters the output makes the declared corpus commit
stale, and the corpus can only be regenerated with a RELEASED generator — so a
pull-request gate would be red by construction for exactly the change it should inform,
and it would deadlock the chain that repairs it (generator merged and tagged → the
corpus regenerates with that tag → the pin is bumped here). It would also be a de-facto
required check: the org pr-validator's `arm` job arms native auto-merge only when
EVERY check on the head is green.

**Two more defects, found in passing.**

- `task marketplace:pin`'s second step compared the corpus's `main` head against the
  file's LAST 40-hex string — which is the sha256 prefix of the byte-identical SKILL.md
  the candy's file records, not a pin. The step could never be true. Each occurrence is
  now found by its ANCHOR (`MARKETPLACE_REF:` and `contains:`), which a third string
  cannot satisfy. The same anchoring is what the CI job reads the baseline with.
- The `setup` launcher and the `.claude/hooks` surface were removed at source in
  2026.241.1105, but the README, the box description, the candy's description, the
  plugin's package comments and the prune boundary still described them as shipped.
  They are gone from the prose, and the generator's own test
  (`assertNotWritten(t, out, "setup")`) is the truth they now match.
